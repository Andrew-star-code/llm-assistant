## [Unreleased]

### Added

- Управление контекстом в генерации (§8.1, §8.3, §8.4 SPEC):
  - бюджет контекста соблюдается внутри цикла инструментов (`completions/context.py`): старая
    история → результаты прошлых итераций → обрезка свежих результатов поровну; в трассировке
    сообщения — `context`; не помещается сам вопрос — ошибка `context_overflow`;
  - описания инструментов входят в бюджет, история оставляет место под результаты
    (`tools.context_reserve_share`, по умолчанию 0,15);
  - прошлые вызовы инструментов и начало их результатов идут в историю диалога
    (`tools.history_result_max_chars`, по умолчанию 2000; 0 — выключено);
  - fake-llm: сценарий `recall`, диапазон страниц «стр. N–M» для `read_document`.
- Генерация вынесена из `api` в сервис `generator` ([ADR-0013](docs/adr/0013-generation-executor.md)):
  `api` ставит задание в очередь Redis, исполнитель ведёт ответ; перезапуск `api` не прерывает
  ответы, `generator` по SIGTERM дорабатывает свои; предел параллельных ответов
  `generation.max_concurrent`; CLI `generator run|check`; режим `generation.mode: inline` для
  тестов. **При обновлении:** в compose появился сервис `generator` — без него в режиме `queue`
  ответы не начинаются.
- Наблюдаемость (§16.6): метрики генерации, очереди исполнителя, инструментов и SSE
  (`core/metrics.py`); порт метрик у `generator` (`generation.metrics_port`); инцидент
  `generator_health`, когда нет исполнителя; очередь генерации и число исполнителей на дашборде
  админки; `deploy/monitoring/` — цели сбора и правила алертов Prometheus с тестами
  (`make test-monitoring`, входит в `make check`).
- Файлы первого запуска на сервере (этап 10а): `deploy/compose/compose.prod.yml` (приложение с
  `generator`, фронтенд, nginx с TLS, модели `llm-chat`, `llm-utility`, `embed`, `rerank`),
  шаблон `deploy/nginx/`, `deploy/backup/backup.sh`, `config/models.prod.yaml`,
  `config/app.prod.yaml.example`; проверки без сервера — `make test-nginx`, `make test-backup`
  (входят в `make check`). `models.<роль>.deployed: false` — монитор здоровья не проверяет ещё
  не развёрнутую модель. Нагрузочный тест: `--ca-file` для портала с корпоративным CA.
- Smoke-проверка стенда `scripts/smoke.py` (`make smoke`): вход и профиль, ответ потоком и
  заголовок, вопрос по файлу, документ Word, переподключение к потоку, модели и исполнитель в
  админке. Руководство `docs/runbooks/backup-restore.md`; `make test-backup` проверяет и
  восстановление Qdrant из снапшота.
- Инцидент `tool_loop_limit` (warning), когда цикл инструментов исчерпал шаги (§8.4); не чаще
  раза в `tools.incident_throttle_s`.
- Нагрузочный тест чата `eval/load/run.py` и `make load-test` (§18.4): N одновременных диалогов
  тем же путём, что браузер, отчёт по приёму сообщения, времени до первого токена и скорости;
  fake-llm: сценарий `stream:<слов>:<пауза, мс>`.
- Живучесть генерации: автоповтор запроса к модели при кратком сбое до первого слова ответа
  (`chat.model_retries`, `chat.model_retry_backoff_seconds`); в трассировке — `model_retries`;
  fake-llm: сценарий `flaky`.

### Changed

- Синхронизация пользователей с AD — задачей `users.ad_sync` по расписанию `scheduler` (выполняет
  `worker`), а не фоновой задачей `api` под блокировкой Redis. **При обновлении:** воркеру нужны
  сеть до контроллеров и секреты AD (в `compose.prod.yml` и `compose.dev.yml` они уже есть).
- `admin/router.py` разделён: журналы входов и аудита и диагностика AD — в
  `admin/journals_router.py`; пути и схемы API не менялись.
- `completions/generation.py` (1232 строки) разнесён по шагам без изменения поведения:
  `state.py`, `preparation.py`, `retrieval.py`, `toolloop.py`, `finish.py`; в `generation.py`
  остались жизненный цикл задач и порядок шагов.

### Fixed

- Модель с малым контекстом (8–16 тыс. токенов) отказывала на любом сообщении с большим
  вложением («Сообщение слишком длинное»): блок вложений и фрагменты авто-поиска не ужимались
  под остаток после инструкций и описаний инструментов. Теперь ужимаются; отказ, когда не
  помещаются сами инструкции и инструменты, называет причину (`context_overflow`). Найдено
  проверкой на рабочей станции.
- Ответ, оборванный по пределу длины (`finish_reason: length`), сохранялся «завершённым» без
  пометки, иногда пустым; теперь к нему добавляется пометка для пользователя.
- Дев-стенд: `generator` под `watchfiles` обрывал ответы через 5 с при остановке и правке кода.
- Дашборд админки: ноль исполнителей генерации не был выделен цветом.
- `make smoke` зависел от документов базы знаний на стенде.
- Открытый SSE-поток держал соединение с PostgreSQL в открытой транзакции до конца ответа: сверх
  ~20 одновременных ответов весь api вставал в очередь за соединением (найдено `eval/load`).
- Читатель SSE обрывался с ошибкой при паузе в ответе дольше 5 с (тайм-аут чтения клиента Redis
  по умолчанию меньше `chat.heartbeat_seconds`); пул Redis был ограничен 100 соединениями —
  теперь `redis_max_connections` (1000).
- Длинный чат с инструментами: история занимала весь контекст, и первый же результат
  инструмента приводил к ошибке модели вместо ответа.
- Ожидаемые отказы генерации (`message_too_long`, `context_overflow`) больше не заводят инцидент
  `system_error` и не предлагают «Повторить».
