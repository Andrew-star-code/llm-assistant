### Added

- Этап 6 «Админка: переписка, аналитика, настройки» (§19 SPEC):
  - **Переписка**: поиск по всем сообщениям (русская морфология и подстрока, подсветка) с
    фильтрами по пользователю, отделу, периоду, сценарию, модели, удалённым, дизлайкам, инцидентам и
    вложениям; список чатов; просмотр чата целиком (все ветки, удалённое, размышления, скрытые
    вызовы инструментов, источники, трассировка) с записью в аудит; «Вернуть пользователю»;
    физическое удаление (только superadmin, подтверждение id);
  - **Выгрузки** (миграция 0007, `exports`): одного чата или выборки — JSON, XLSX, DOCX, PDF фоновой
    задачей; файл только заказавшему, 7 дней; сервис `scheduler` (Celery beat) — очистка истёкших
    выгрузок и удалённого по сроку хранения (по умолчанию выключено);
  - **Обратная связь**: оценки с причинами и комментариями, статистика, переход в чат, XLSX;
  - **Дашборд**: активные пользователи, сообщения и токены по дням, время до первого токена,
    популярные сценарии, доля ошибок и лайков, состояние моделей, очереди, инциденты, GPU из
    Prometheus/DCGM;
  - **Модели**: реестр, проверка эндпоинтов, видимость по ролям (скрывает сценарии);
    **Инструменты**: включение и выключение, статистика вызовов;
  - **Настройки**: название и логотип (страница входа и боковая панель), компания, уведомление при
    первом входе с повторным подтверждением, срок хранения, лимиты файлов, обращение по умолчанию,
    базовый системный промпт — без перезапуска, с аудитом;
  - девять новых прав; README `admin`, `exports`, `feedback`, guides, `permissions.md`.

- `eval/rag`: вопросы без ответа в корпусе (`no_answer`, отдельно от hit@5/MRR), перебор порога
  реранкера по трассе и `recommended_threshold`; `make eval-rag` пишет `eval/rag/report.json`;
  прогон по настоящим базам знаний (`make eval-rag KB=<коды> QUESTIONS=<файл>`, документ — по
  названию, без переиндексации).
- Админка «Базы знаний» → «Параметры поиска»: порог реранкера меняется без перезапуска
  (`GET/PUT /api/admin/kb/search-settings`, `app_settings`, аудит), «Вернуть из конфигурации».
- Вложения «в очереди» и «в обработке» возвращаются в очередь при старте воркера `files`
  (`files.requeue`); `worker check` проверяет, что все таблицы зарегистрированы.

### Changed

- Порог реранкера `rag.search.rerank.score_threshold` 0,2 → 0,005, с уклоном в полноту поиска:
  на bge-m3 и bge-reranker-v2-m3 с 0,2 рабочая конфигурация теряла 7 из 48 ответов. Окончательное
  значение подбирается на реальных документах.
- Дев-стенд: healthcheck embed и rerank ждут до 30 минут (`--wait-timeout 2100`), реранкер
  стартует после готового embed и не перезапускается вместе с Docker (одновременный прогрев не
  помещается в память WSL2); `pnpm` в Makefile запускается из `frontend/` (corepack берёт версию
  из `packageManager`).

- Реранкер в формате text-embeddings-inference (`models.rerank.api: tei`): `/rerank` с полем `texts`,
  пакетами по 32; сервис `rerank` (TEI, bge-reranker-v2-m3) в профиле `models` дев-стенда
  (`make dev-models-up`), `deploy/compose/api.local.env.example`; `eval/rag` печатает модели прогона,
  ждёт реранкер до 120 с (`--rerank-timeout`) и проваливает `--check`, если стадия пропущена;
  инструкция прогона на рабочей станции с WSL2 (`eval/README.md`).

### Fixed

- Воркеры и CLI (`kb import`) не регистрировали все модели SQLAlchemy: задачи на настоящем Celery
  падали на внешних ключах (`files.chat_id`, `kb_imports.created_by`). Тесты с eager-воркером этого
  не видели — добавлена проверка импорта в отдельном процессе.
- Непредвиденная ошибка задачи воркера оставляла вложение «читаю…», документ базы «в обработке», а
  импорт «сканирование»: теперь статус «ошибка» с причиной и инцидент `worker_failed`.
- `make eval-rag` / `eval-scenarios`: отчёт не записывался в смонтированный `eval/` (права uid
  контейнера) — контейнер запускается от пользователя хоста.
- e2e: гонка в `admin.spec` на дев-сервере Vite; проверка PDF-превью в `files.spec` обязательна при
  `E2E_REAL_WORKER=1`.
- Удаление открытого чата иногда не возвращало на стартовый экран (колбэк мутации терялся при
  размонтировании пункта истории).
- Параллельные инструменты писали события в Redis Stream одновременно — часть событий терялась
  с ошибкой порядка id; запись теперь последовательная.
- fake-llm: заголовок чата, начатого с маркера сценария, строился по ответу сценария.
