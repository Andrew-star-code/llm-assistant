## 3. Дефекты

### Дефект 1 🔴. `mock-mssql` падает на старте с заполненным томом, `make check` плавающий

Шаги: поднять стенд → `make test-data-gateway`, повторить несколько раз.

Ожидаемо: контейнер стартует, самопроверка идёт. Фактически до шлюза дело не доходит:

```text
Container ai-assistant-mock-mssql-1 Recreate
container ai-assistant-mock-mssql-1 is unhealthy
make: *** [Makefile:128: test-data-gateway] Error 1
```

В логе контейнера при этом, иногда несколько раз подряд:

```text
Msg 904, Level 16, State 3
Database 5 cannot be autostarted during server shutdown or startup.
```

**Причина подтверждена.** SQL Server принимает вход раньше, чем восстановлена база `corp`. `entrypoint.sh` ждёт только `SELECT 1`, затем `USE corp` в `seed.sql`
падает, `-b` и `set -e` завершают контейнер, а `--wait` считает это отказом. Со свежим томом гонки нет, поэтому первый `make dev-up` проходит. Сам контейнер
через 21–54 с поднимается благодаря `restart: unless-stopped`.

**Почему срабатывает так часто.** Образ без изменений получает новый id при каждой сборке (`ab87…`, `3d59…`, `817f…`, три сборки подряд), поэтому `--build` всякий раз
пересоздаёт контейнер. Предположительно, дело в метаданных сборки. Это же, скорее всего, объясняет наблюдение этапа 7 о пересоздании `fake-llm` и `mock-ad`.

| Что | Исходный код | С правкой |
| --- | --- | --- |
| `make test-data-gateway`, успешно | 5 из 9 | **8 из 8** |
| Перезапуски с падением контейнера | 6 из 16 | **0 из 8** |
| `Msg 904` в логе | есть | есть, но повторяется внутри `entrypoint`, контейнер не падает |

**Правка** — отдельный коммит в этой ветке, только `deploy/mock-mssql/entrypoint.sh`: `seed.sql` идемпотентен, поэтому применяется с повтором, до 30 раз через 2 секунды. На
продукт не влияет, контейнер только для дев-стенда.

### Дефект 2 ⚠️. При остановленном шлюзе пользователь не видит причину

Шаги: `docker compose … stop data-gateway` → «Кадровый бот» → «Найди телефон Петрова из бухгалтерии».

Ожидаемо по задаче: понятная ошибка шага «шлюз данных недоступен». Фактически ([скриншот](assets/stage9/11-gateway-down.png)):

```text
шаг:                  Ищу в справочнике: «Петров» — ошибка
ответ:                В телефонном справочнике никого не нашёл.
результат инструмента: error | Ошибка: шлюз данных недоступен
```

Падения ответа нет, причина сохранена в `tool_calls` и в журнале. Но ответ fake-llm вводит в заблуждение: сотрудник есть, недоступен шлюз. Источник —
`phonebook_answer` в `services/fake-llm/src/fake_llm/scenarios.py`, он считает любой результат без таблицы пустым. Настоящая модель получит текст ошибки, как она ответит, не проверялось.

### Разовый сбой: 11 таймаутов Vitest

Прогон длился 13 с вместо обычных 6. Причина не установлена. Правка фронтенд не затрагивает. Следующий `make check` на том же дереве и 3 отдельных прогона `make test-frontend`
прошли. Всего сбой случился 1 раз из 7. Если повторится, стоит посмотреть на запас тайм-аута 5 с под нагрузкой сразу после pytest.

### Задача и демо: что расходится со стендом

- **«SQL только на DEBUG».** В коде шлюза нет `log.debug`, SQL не пишется ни на каком уровне. Для безопасности это лучше, но `DG_LOG_LEVEL: DEBUG` в `compose.dev.yml` ничего не даёт. Отказы
  в логе шлюза тоже не видны: они есть только в аудите api.
- **«В ответе раздел «Примеры»».** На fake-llm раздела в тексте ответа нет, он в результате инструмента.
- **Демо, подбор примеров.** На штатном каталоге подбор по смыслу не включается, см. выше.

### Наблюдения, не дефекты

- **В аудите у запросов из чата нет IP,** у тестового вызова из админки он есть.
- **Все запреты изменения дают один текст.** `EXEC xp_cmdshell` назван «изменением данных»: понятно, но неточно.
- **`Осталось попыток: 2` в ответе** появляется при каждом отказе: счётчик идёт на ответ, а каждое сообщение — новый ответ.
