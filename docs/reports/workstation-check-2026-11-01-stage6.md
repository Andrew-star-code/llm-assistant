## 3. Дефекты

### Дефект 1 ❌. `scheduler` всегда `unhealthy`, `make dev-up` падает

Шаги:

```bash
make dev-up
```

Ожидаемо: код 0, все сервисы работают. Фактически, код 2 на работающем стенде:

```text
19:29:46 container ai-assistant-scheduler-1 is unhealthy
19:29:46 make: *** [Makefile:38: dev-up] Error 1
```

**Причина подтверждена.** `scheduler` запускается из образа `ai-assistant/api`, а `backend/Dockerfile` задаёт
там `HEALTHCHECK` на `http://127.0.0.1:8000/health`. Beat порт не слушает:

```text
"Status":"unhealthy","FailingStreak":4, … ConnectionRefusedError: [Errno 111] Connection refused
```

Сам beat исправен, и рестартов нет, поэтому на функциях это не сказывается. Но `--wait` возвращает ошибку, из-за
чего сценарии вида `make dev-up && …` останавливаются. `make check` этого не видит: он не поднимает стенд.
В песочнице образы не собирались.

Исправление — отдельный коммит этой ветки, по образцу `HEALTHCHECK NONE` у воркера:

```diff
--- a/deploy/compose/docker-compose.yml
+++ b/deploy/compose/docker-compose.yml
@@ scheduler
               "--schedule", "/tmp/celerybeat-schedule", "--loglevel", "INFO"]
+    healthcheck:
+      disable: true
     environment:
```

Проверено: с этой правкой `make dev-up` на том же стенде завершился кодом 0 за 0:29, `scheduler` в состоянии `Up`, `RestartCount=0`, `beat: Starting...`, схема `0007`.

### Дефект 2 ⚠️. После сохранения настроек нет подтверждения

Шаги: «Настройки» → изменить название → «Сохранить».

Ожидаемо: надпись «Сохранено — действует без перезапуска». Фактически значение сохраняется, но надпись не
появляется ни на миг. `MutationObserver` на странице записал 0 элементов `role=status` и `role=alert`:

```text
PUT /api/admin/settings → 200
за всё время на странице появлялись status/alert: []
после сохранения app_name=Помощник!, в поле: Помощник!
```

**Причина подтверждена по коду.** `SettingsForm` создаётся с `key={JSON.stringify(settings.data)}`. Новые данные
меняют ключ, форма монтируется заново, и `useState(saved)` сбрасывается. Надпись увидят только при сохранении
без изменений. Вариант исправления, не проверялся: держать `saved` в родительском `SettingsPage`.

### Дефект 3 ⚠️. «Импорт из папки идёт» на дашборде залипает

Шаги: дождаться конца импорта в базу, не открывая её страницу → открыть дашборд.

Ожидаемо: 0. Фактически импорт `4b5a71b9` из прошлой проверки был создан в 11:00 UTC и всё ещё считался идущим
в 15:48 UTC, хотя все документы готовы и очереди пусты:

```text
очереди до открытия базы:                {"imports_running":1, "kb_queued":0, "kb_processing":0, …}
очереди после открытия страницы базы:    {"imports_running":0, "kb_queued":0, "kb_processing":0, …}
```

**Причина подтверждена.** В `done` импорт переводит только чтение: `kb.service.import_out`. Дашборд считает строки
со статусом `running` напрямую. `kb.requeue` такой импорт не трогает, он выбирает только `scanning`. Вариант
исправления, не проверялся: завершать импорт в воркере после последнего документа или считать на дашборде только
импорты с документами в очереди.

### Дефект 4 ⚠️. `kb_manager` без баз видит форму создания базы

Шаги: выдать `kim` только `kb_manager` → «Базы знаний» → заполнить «Новая база знаний» → «Создать».

Ожидаемо: формы нет, у роли нет `admin.kb.manage`. Фактически форма есть, а отправка даёт отказ:

```text
POST /api/admin/kb → 403; на странице: ["Недостаточно прав"]
```

**Причина подтверждена по коду.** В `KbListPage` стоит `canCreate = bases.data.every((b) => b.can_edit)`, и на
пустом списке это истина. Защита на сервере работает, утечки прав нет. Вариант исправления, не проверялся:
`hasPermission(me, "admin.kb.manage")`.

### Демо в `docs/status.md`: шаг 10 расходится со стендом после `make e2e`

- **Код `legal` занят.** Роль `legal` заводит правило `ldap.department_roles`, когда входит сотрудник юротдела. Форма
  отвечает «Роль с таким кодом уже есть». В проверке взят код `legal_demo`; в демо стоит указать другой код.
- **`sidorova` уже входила.** Её логинят `auth.spec.ts` и `scenarios.spec.ts`. Чтобы выполнить условие, её строка удалена
  из дев-базы вместе с 10 записями `login_events` и 10 `sessions`; чатов, файлов и записей аудита у неё не было. После
  этого она заведена из AD заново. В демо стоит взять `smirnova`, которую e2e не использует, или добавить этот шаг.

## 4. Что не проверено

- **Модели настоящие не подключались:** всё шло через fake-llm. Он вызывает инструмент по маркеру, поэтому при
  выключенном `create_document` проверен отказ сервера и отсутствие файла. То, что инструмент не предлагается
  модели, закрывает только `test_admin_sections.py`.
- **Скрытые вызовы инструментов** в просмотре чата на стенде не создавались, это закрывает `test_admin_chats.py`.
- **Шесть тестов pytest** не запускались внутри образа воркера. Их функции проверены `make test-worker` и демо.
- **Лимит файла** проверен только через интерфейс, прямой вызов API не проверялся.
- **Очистка по сроку чата с вложением:** в проверенном чате файлов не было; файлы при ручном удалении
  проверены, это тот же `purge_chat`.
- **`retention.purge` по расписанию** не дождались: первый запуск через 6 часов. Вручную задача выполнена на `worker`.
- **Демо пройдено скриптом**, а не руками. Ключевые экраны просмотрены по скриншотам.

## 5. Наблюдения по окружению

- **Время.** `make dev-up` — 13:53, из них 13:02 сборка образов: дольше всего шла установка пакетов образа
  воркера с `deb.debian.org`. Запуск контейнеров 0:51. Повторный запуск с исправлением без пересборки — 0:29.
- **Память.** WSL 22 ГБ. На стенде занято 15 ГиБ, свободно 5,8 ГиБ, из них `embed` 12,3 ГиБ, `worker` 0,75 ГиБ. Зависаний
  и заметного swap (207 МиБ) нет. Реранкер не запускался.
- **`worker` не ждёт `embed`.** При старте `files.requeue` перечитал 5 файлов с прошлой проверки, пока `embed` прогревался:
  воркер готов в 15:29:10, `embed` в 15:29:48. Файлы получили `ready` с `worker.index_failed: Connection error` и остались
  без индекса поиска. Они читаются целиком, но `search_in_documents` их не найдёт. На работающем стенде это не
  воспроизводится.
- **Расписание beat живёт в `/tmp` контейнера,** а интервал отсчитывается от старта. Вывод из кода, не проверялось:
  если `scheduler` пересоздавать чаще раза в 6 часов, `retention.purge` не сработает ни разу.
- **Часовые пояса выгрузки.** Для одного чата: в имени файла UTC (`15-39`), внутри файла `chat.timezone` (18:38), в
  интерфейсе пояс браузера (19:39). Имя собирает `utcnow().astimezone()` в контейнере с UTC.
