# Задача: проверить на рабочей станции доработки архитектуры (ветка `ccr-024c8c3b-cnj7hg`)

Ты работаешь в репозитории корпоративного ИИ-ассистента на рабочей станции разработчика: Windows +
WSL2, Docker Desktop. Правила проекта — в `AGENTS.md`, требования — в `docs/SPEC.md`, что сделано в
ветке — в `docs/status.md` (разделы «Доработка: …» после этапа 9) и в `CHANGELOG.md` (`Unreleased`).
Общайся и пиши отчёт на русском. Образец отчёта —
`docs/reports/workstation-check-2026-11-02-stage9.md`.

**Рабочая станция изолирована: настоящего Active Directory, GPU и сервера нет.** Всё, что касается
AD, проверяется на контейнере `mock-ad` дев-стенда (Samba AD DC, пользователи — в
`deploy/mock-ad/README.md`, пароль `Passw0rd!`). Не пытайся подключаться к внешним контроллерам,
не меняй `ldap.urls` и не считай отсутствие настоящего AD дефектом. Вход через настоящий AD,
настоящий TLS и запуск моделей на GPU проверяются только на сервере — в отчёте перечисли их как
«не проверялось, вне возможностей стенда».

## Цель

В ветке шесть доработок, сделанных в облачной песочнице: управление контекстом, живучесть и вынос
генерации в сервис `generator`, наблюдаемость, нагрузочный тест с двумя исправлениями, файлы первого
запуска (этап 10а), декомпозиция генерации и технический долг. В песочнице **не собирались образы
приложения** (сеть внутри `docker build` закрыта), поэтому там не проверено:

- `make check` целиком и сборка образов `api`, `worker`, `data-gateway`, `frontend`;
- дев-стенд через `make dev-up` с новым сервисом `generator` (healthcheck, перезапуск при правке
  кода, доработка ответов при остановке);
- `make e2e`, `make smoke`, `make load-test` против стенда из контейнеров;
- синхронизация с AD задачей планировщика в контейнере `worker`;
- новые строки дашборда админки и новые типы инцидентов в браузере.

Нужно подтвердить всё это и решить, можно ли вливать ветку в `main`. **Код продукта не меняй.**
Найдёшь дефект — опиши его с шагами воспроизведения; исправление можно предложить отдельным
коммитом в своей ветке.

### 2. Исполнитель генерации (`generator`, ADR-0013)

Читай `docs/adr/0013-generation-executor.md` и «Демо-сценарий (исполнитель)» в `docs/status.md`.
Для долгого ответа используй `[[scenario:stream:300:100]] проверка` (около 30 секунд).

- **Перезапуск api не прерывает ответ.** Отправь долгое сообщение в браузере
  (http://localhost:5173, вход кнопкой dev), во время ответа выполни `$DC restart api`. Ожидается:
  ответ продолжает печататься после короткой паузы и завершается; статуса «Генерация прервана» нет.
- **Очередь переживает отсутствие исполнителя.** `$DC stop generator`, отправь обычное сообщение —
  ответ ждёт (пустой, без ошибки). `$DC start generator` — ответ начинается и завершается.
- **Остановка дорабатывает ответ.** Отправь долгое сообщение и сразу `$DC stop generator`: команда
  ждёт (до 200 с), ответ в чате дописывается до конца, статус — завершён, а не прерван. Запиши,
  сколько длилась остановка. Затем `$DC start generator`.
- **Healthcheck.** `$DC exec generator python -m app.cli generator check` — «исполнитель работает»,
  код 0; у остановленного сервиса `ps` показывает его не `healthy`.
- **Перезапуск при правке кода.** Добавь и убери пустую строку в любом файле
  `backend/app/modules/completions/` — в логах `generator` видно перезапуск (`generator.stopped`,
  `generator.started`), после него ответы работают. `git status` должен остаться чистым.
- **Логи.** В логах `generator` нет `Traceback`; у строк генерации есть `request_id`, совпадающий
  со строкой запроса в логах `api`; на уровне INFO нет текстов сообщений пользователя.

### 3. Наблюдаемость

- **Метрики исполнителя** (порт наружу не опубликован — запрос изнутри контейнера):
  ```bash
  $DC exec generator python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:9100/metrics').read().decode())" | grep -E "^app_generation"
  ```
  После нескольких ответов: `app_generations_total{role="chat",status="completed"}` растёт, есть

- **Метрики api:**
  ```bash
  $DC exec api python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/metrics/').read().decode())" | grep -E "^app_(generation_queue_length|generation_executors|sse_connections)"
  ```
  Ожидается `app_generation_executors 1.0`, очередь `0.0`.
- **Дашборд админки** (вход `ivanov`): в блоке «Очереди» — строки «Ответы в очереди генерации» и
  «Исполнителей генерации: 1». Останови исполнитель — в течение нескольких секунд после обновления
  страницы «0» красным. Скриншоты обоих состояний.
- **Инцидент `generator_health`.** При остановленном исполнителе подожди 2–3 минуты: в «Инцидентах»
  появляется запись «Нет исполнителя генерации…» уровня critical, тип «Исполнитель генерации» есть
  в фильтре. Запусти исполнитель — через минуту в карточке инцидента системный комментарий о
  восстановлении. Задачу ставит `scheduler`, выполняет `worker`: если инцидента нет — приложи их логи.
- **Инцидент `tool_loop_limit`.** Приложи к чату любой текстовый файл и отправь

  warning «Цикл инструментов: превышено число шагов (8)», тип «Лимит шагов инструментов» в фильтре;
  в данных инцидента нет текста сообщения.

### 5. Синхронизация с AD в планировщике (на mock-AD)

Раньше синхронизацию вёл `api`, теперь — задача `users.ad_sync` в `worker`.

1. В окне инкогнито войди через AD: логин `smirnova`, пароль `Passw0rd!` (форма входа, не кнопка dev).
2. Отключи учётку в mock-AD:
   ```bash
   $DC exec mock-ad samba-tool user disable smirnova
   ```
3. Запусти задачу, не дожидаясь расписания (оно — на 47-й минуте каждого часа):
   ```bash
   $DC exec worker celery -A app.workers.celery_app call users.ad_sync
   ```
   Команда в песочнице не проверялась. Если она не сработала — приложи вывод и дождись 47-й минуты.
4. Ожидается: в логах `worker` строка `users.sync.done` с `disabled=1` и `errors=0`; вкладка
   `smirnova` после обновления — на странице входа; в админке у пользователя отметка «отключён в AD».
5. Верни как было и повтори задачу:
   ```bash
   $DC exec mock-ad samba-tool user enable smirnova
   ```
   `smirnova` снова входит.
6. В логах `api` за время проверки нет строк `users.sync.*` — синхронизацию он больше не ведёт.
7. В логах `worker` нет ошибок чтения секрета или сертификата (`ldap_bind_password`,

```bash

```

Ожидается: 50 из 50 завершено, три «да» в целях §18.4. Запиши строку времени до первого токена.

```bash
uv run python eval/load/run.py --concurrency 50 --messages 150 --admin ivanov
```

Ожидается: все 150 завершены, приём сообщения (POST) p95 — около секунды или меньше, время до
первого токена p95 — единицы секунд. **Это проверка двух исправлений** (соединения с БД у SSE и
тайм-аут Redis): если POST p95 — около 10 с или есть обрывы (`failed`, `RemoteProtocolError`) —
дефект, приложи отчёт и логи `api`. Во время прогона сними:

```bash
$DC exec postgres psql -U assistant -d assistant -Atc "select state, count(*) from pg_stat_activity where datname='assistant' group by 1"
```

Соединений в состоянии `idle in transaction` должно быть единицы, а не десятки.

Прогон создаёт персональные политики лимитов на 2 часа (видны в админке «Лимиты») и чаты тестовых
пользователей — отметь это в отчёте, удалять не обязательно.
