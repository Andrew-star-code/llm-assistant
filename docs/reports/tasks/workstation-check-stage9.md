# Задача: проверить этап 9 (семантический слой и SQL) на рабочей станции

Ты работаешь в репозитории корпоративного ИИ-ассистента на рабочей станции разработчика: Windows + WSL2,
Docker Desktop. Правила проекта — в `AGENTS.md`, требования — в `docs/SPEC.md` (§9.5 — семантический
слой), прогресс и демо — в `docs/status.md` (раздел «Этап 9»). Общайся и пиши отчёт на русском. Образец
отчёта — `docs/reports/workstation-check-2026-11-01-stage7.md`.

Если этап 8 ещё не проверен, сначала выполни `docs/reports/tasks/workstation-check-stage8.md` (можно в
одной ветке и одном прогоне `make check`, отчёты — отдельные).

## Цель

В облачной песочнице **образ шлюза `data-gateway` с Microsoft ODBC Driver 18 не собирался** (зеркала
Debian закрыты): шлюз запускался на хосте с драйвером pymssql против настоящего контейнера MS SQL. Нужно
подтвердить на рабочей станции, что образ собирается и работает через pyodbc, и пройти критерии и демо
этапа 9. **Код продукта не меняй.** Найдёшь дефект — опиши его с шагами воспроизведения; исправление
можно предложить отдельным коммитом в своей ветке.

### 2. Шлюз на стенде
- `curl http://localhost:8090/health` → `{"status":"ok","catalog_error":null}`.
- Без подписи запрос отклоняется: `curl -s http://localhost:8090/v1/catalog` → 401.
- В логах `data-gateway` нет `Traceback`; строки `dg.done … rows=…` при запросах; на уровне INFO нет
  текста SQL (он только на DEBUG — на дев-стенде включён DEBUG, проверь, что INFO-строки без SQL).
- Логин `dg_reader` только на чтение: через `docker compose … exec mock-mssql
  /opt/mssql-tools18/bin/sqlcmd -C -S localhost -U dg_reader -P <пароль из .env> -d corp -Q "UPDATE
  dbo.v_phonebook SET phone = N'1'"` — отказ «UPDATE permission was denied»; `SELECT salary FROM
  dbo.employees` — отказ.

### 3. Демо этапа 9
Пройди 6 шагов «Демо-сценария» этапа 9 из `docs/status.md` в браузере на http://localhost:5173.
Особое внимание:
- **Критерий 1.** «Кадровый бот» → «Найди телефон Петрова из бухгалтерии» → номер +7 (495) 100-20-02,
  внутренний 2002; шаг «Ищу в справочнике: «Петров»» со статусом «готово».
- **Критерий 2.** Запросы `DELETE`, `UPDATE`, `DROP`, `EXEC xp_cmdshell 'dir'`, `SELECT salary FROM
  dbo.employees`, `SELECT * FROM dbo.v_phonebook` через `[[scenario:tool:run_sql_query]] …` — каждый
  отклонён понятным текстом, данные в справочнике не изменились.
- **Критерий 3.** Каждый запрос из шагов выше виден в «Источниках данных» (журнал) и в «Аудите»
  (`data.query` / `data.function`): пользователь, SQL, статус, число строк, время, ссылка на чат.
- **Большой результат.** Запрос, возвращающий больше 50 строк, на тестовом справочнике не получить —
  проверь, что CSV-карточка появляется хотя бы с временной правкой `APP_DATA_GATEWAY__PREVIEW_ROWS=2`
  в `deploy/compose/api.local.env` (потом удали) на запросе `SELECT full_name FROM dbo.v_phonebook`.
- **Похожие примеры.** `[[scenario:tool:describe_dataset]] телефон` — в ответе раздел «Примеры» (до 5);
  с работающим `embed` они подбираются по смыслу вопроса.
- **Каталог без перезапуска.** Шаг 6 демо: ошибка в YAML видна в «Источниках данных», поиск работает;
  после исправления ошибка пропадает. Верни файл (`git status` чистый).
- **Права.** У `petrov` раздела «Источники данных» нет, `/api/admin/data/catalog` → 403.
- **Перезапуск.** `docker compose … restart data-gateway` во время пустого стенда — api переживает;
  вопрос в «Кадровом боте» во время остановленного шлюза даёт понятную ошибку шага («шлюз данных
  недоступен»), а не падение ответа.
