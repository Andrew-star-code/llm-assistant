# Задача: проверить приложение на боевом сервере с настоящими моделями (до первого запуска)

Ты работаешь на боевом GPU-сервере корпоративного ИИ-ассистента (4× A100). Правила проекта — в
`AGENTS.md`, требования — в `docs/SPEC.md`, что сделано и что осталось — в `docs/status.md`
(раздел «Проверка на рабочей станции и исправления по её итогам»). Общайся и пиши отчёт на русском.

**Состояние сервера: работают (или могут быть запущены) только модели; приложение не развёрнуто,
пользователей нет.** Первый запуск приложения — отдельное событие по
`docs/runbooks/first-deploy.md`, его проводит человек. **Эта задача — не первый запуск.** Ты
проверяешь модели и поднимаешь рядом временный проверочный стенд приложения, который после
проверки удаляешь без следа.

## Цель

На рабочей станции не удалось проверить то, для чего нужен настоящий vLLM и боевые модели:

1. флаги vLLM из `deploy/compose/compose.prod.yml` (парсеры размышлений и вызова инструментов);
2. предел контекста: приложение не должно доводить до отказа модели по длине промпта;
3. исправления дефектов 4 и 5 из отчёта от 12 ноября (малый контекст, оборванный ответ) — на
   живой модели;
4. цели §18.4 SPEC на настоящей модели: время до первого токена и скорость при 10 одновременных
   диалогах — критерий приёмки этапа 10;
5. имена метрик vLLM, на которые опираются алерты `deploy/monitoring/alerts.yml`.

## Жёсткие ограничения

Сервер боевой. Нарушение любого пункта — остановись и спроси человека.

- **Не останавливай и не перезапускай уже работающие контейнеры моделей** и не меняй их флаги.
  Проверки работающих моделей — только запросами к ним. Запустить модель, которая сейчас не
  работает, можно только после подтверждения человека (что и на какой GPU).
- **Не выполняй шаги первого запуска**: не создавай `deploy/compose/.env` и
  `config/app.prod.yaml`, не трогай `/srv/ai-assistant-secrets`, не запускай
  `compose.prod.yml`, nginx и TLS, не обращайся к Active Directory.
- **Проверочный стенд — только проектом `ai-check`** (`-p ai-check`): у него свои тома и сеть.
  Не создавай тома и контейнеры проекта `ai-assistant` — это имя будущего прода. Перед каждой
  командой `docker compose` убедись, что в ней есть `-p ai-check`.
- **Стенд доступен только с самого сервера** (`127.0.0.1:18000`): вход на нём без пароля. Не
  публикуй порт наружу, не меняй привязку адреса, не пробрасывай его через nginx или туннель.
- Не устанавливай системные пакеты, не меняй настройки Docker, драйвера и фаервола.
- Не выводи в отчёт и в терминал ключи API моделей, пароли и содержимое `.env*`.
- Код продукта не меняй. Найдёшь дефект — опиши с шагами воспроизведения; правку можно
  предложить отдельным коммитом в своей ветке.

## Подготовка

1. Репозиторий — отдельная рабочая копия, **не** `/srv/ai-assistant` (он для прода):
   ```bash
   git clone <адрес репозитория> ~/ai-check && cd ~/ai-check
   ```
   ```bash
   git checkout -B agent/server-check origin/ccr-024c8c3b-cnj7hg
   ```
   Если с сервера нет доступа к репозиторию или к реестрам образов — запиши это и спроси
   человека, как доставить код и образы (перенос `docker save` с рабочей станции описан в
   руководстве первого запуска, раздел 8.1).
2. Инвентаризация, только чтение. Запиши в отчёт:
   ```bash
   nvidia-smi
   ```
   ```bash
   docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'
   ```
   Для каждого контейнера модели: образ и его digest, полная команда запуска
   (`docker inspect --format '{{json .Config.Cmd}}' <имя>`), на каких GPU работает, сети
   (`docker inspect --format '{{json .NetworkSettings.Networks}}' <имя>`), ответ `GET /v1/models`
   и `GET /health`. Версия vLLM — из логов старта или `vllm --version` внутри контейнера.
   Какие роли из `config/models.yaml` есть на сервере: `chat`, `utility`, `embed`, `rerank`
   (`coder` и `guard` на первом запуске не нужны).

Запросы к модели, не опубликованной на хосте, делай из временного контейнера в её сети
(`docker run --rm --network <сеть модели> <образ с curl или python> …`) или через
`docker exec <контейнер модели> python3 -c …`.

## Часть A. Модели (без приложения)

### A1. Флаги запуска против `compose.prod.yml`

Сравни фактическую команду каждой работающей модели с её сервисом в
`deploy/compose/compose.prod.yml` (`llm-chat`, `llm-utility`, `embed`, `rerank`): имя модели и
`--served-model-name`, `--max-model-len`, `--tensor-parallel-size`,
`--gpu-memory-utilization`, `--reasoning-parser`, `--enable-auto-tool-choice`,
`--tool-call-parser`, `--enable-prefix-caching`. Таблица «в файле / на сервере / совпадает».
Расхождение — не дефект сервера, а находка для файла: его флаги писались без сервера.

Если чат-модель **не запущена**, спроси человека и, получив подтверждение, проверь, что файл
разбирается и модель стартует с флагами из файла:
```bash
cd deploy/compose && VLLM_IMAGE=<образ по digest> TEI_IMAGE=<образ по digest> PORTAL_HOST=check.local docker compose -p ai-check-models --env-file /dev/null -f docker-compose.yml -f compose.prod.yml config -q
```
Сам запуск — только указанного человеком сервиса и только с `-p ai-check-models`.

### A2. Поведение API чат-модели

Каждый пункт — запрос к `POST /v1/chat/completions`, в отчёт — что пришло (без длинных текстов):

- **Вызов инструмента.** Сообщение «Какая погода в Москве?» и один инструмент `get_weather(city)`
  с `tool_choice: auto` — в ответе `tool_calls` с именем и JSON-аргументами, `finish_reason:
  tool_calls`, а не JSON в `content` (проблема В5 руководства). 3 попытки.
- **Размышления.** С `chat_template_kwargs: {"enable_thinking": true}` рассуждение приходит
  отдельным полем (`reasoning` или `reasoning_content`), а не в `content`; с `false` — рассуждения
  нет. Запиши имя поля.
- **Стрим и учёт.** `stream: true`, `stream_options: {"include_usage": true}` — последний чанк
  содержит `usage` с `prompt_tokens` и `completion_tokens`; есть ли
  `completion_tokens_details.reasoning_tokens`.
- **Предел длины ответа.** `max_tokens: 20` на длинный вопрос — `finish_reason: length`.
- **Предел контекста.** Промпт заведомо длиннее `--max-model-len` (сгенерируй текст нужной
  длины): запиши HTTP-статус и текст ошибки дословно — приложение показывает такой отказ как
  `model_http_<статус>`.
- **Параметры сэмплинга.** Запрос с `top_k`, `presence_penalty` из `config/models.yaml`
  (`sampling.default`) принимается без ошибки.

То же коротко для `utility` (без инструментов): ответ и стрим.

### A3. Эмбеддинги и реранкер

- `POST <embed>/v1/embeddings` с `{"model": "BAAI/bge-m3", "input": ["проверка"]}` — вектор
  длиной **1024**.
- Реранкер в формате TEI: `POST <rerank>/rerank` с `{"query": "отпуск", "texts": ["Отпуск 28
  дней", "Курс валют"]}` — список с `index` и `score`, первый текст выше. Запиши время ответа.

### A4. Метрики vLLM

`GET /metrics` чат-модели: есть ли ряды `vllm:num_requests_waiting` и
`vllm:gpu_cache_usage_perc` (на них написаны алерты `ModelQueueGrowing` и `KvCacheFull` в
`deploy/monitoring/alerts.yml`). Если имена другие (например, `vllm:kv_cache_usage_perc`) —
запиши фактические имена и приложи список всех рядов `vllm:*` (только имена).

### A5. Короткий бенчмарк модели

Если чат-модель свободна (нет чужих запросов — проверь `vllm:num_requests_running`):
```bash
docker exec <контейнер чат-модели> vllm bench serve --model <имя модели> --dataset-name random --random-input-len 2000 --random-output-len 500 --num-prompts 50 --max-concurrency 10
```
Запиши время до первого токена (среднее и p99) и пропускную способность. Если подкоманды нет в
этой версии — запиши и пропусти.

## Часть B. Приложение на настоящих моделях (проверочный стенд)

Стенд описан в `deploy/compose/compose.check.yml` — прочитай комментарий в его начале.

### B1. Поднять стенд

1. Сеть для связи стенда с моделями — подключается к работающим контейнерам **без перезапуска**:
   ```bash
   docker network create ai-check-models
   ```
   ```bash
   docker network connect ai-check-models <контейнер чат-модели>
   ```
   Повтори `connect` для `utility`, `embed`, `rerank`. Запиши имена: после проверки их надо отключить.
2. Настройки:
   ```bash
   cd ~/ai-check/deploy/compose && cp check.models.env.example check.models.env
   ```
   Впиши имена контейнеров, порты **внутри** контейнеров и имена моделей из `GET /v1/models`.
   `CONTEXT_LENGTH` — не больше `--max-model-len` чат-модели. Роли, которой на сервере нет,
   оставь адрес несуществующего контейнера и отметь это в отчёте: проверки, которым она нужна,
   пропускаются (без `utility` заголовок чата берётся из первых слов вопроса; без `embed` и
   `rerank` — нет поиска по вложениям и базам).
   ```bash
   { echo "POSTGRES_PASSWORD=$(openssl rand -hex 16)"; echo "REDIS_PASSWORD=$(openssl rand -hex 16)"; echo "QDRANT_API_KEY=$(openssl rand -hex 16)"; echo "APP_VERSION=check"; } > .env.check
   ```
3. Сборка и запуск (`DCC` — сокращение, **всегда с `-p ai-check`**):
   ```bash
   DCC="docker compose -p ai-check --env-file .env.check -f docker-compose.yml -f compose.check.yml"
   ```
   ```bash
   $DCC build api worker
   ```
   ```bash
   $DCC up -d
   ```
   Ожидается: `postgres`, `redis`, `qdrant`, `api`, `generator` — `healthy`; `migrate` — `exited
   (0)`; `worker`, `worker-kb`, `scheduler` — `running`. Проверь, что порт привязан к localhost:
   `docker port ai-check-api-1` → `127.0.0.1:18000`.
4. Самопроверки:
   ```bash
   curl -s http://127.0.0.1:18000/api/auth/providers
   ```
   ```bash
   $DCC exec generator python -m app.cli generator check
   ```
   ```bash
   $DCC exec worker python -m app.cli worker check
   ```
5. Инструменты запуска скриптов на сервере: `uv` (или Python 3.12 с `httpx`). Если `uv` нет и
   ставить нельзя — запускай скрипты из контейнера:
   `docker run --rm --network host -v ~/ai-check:/w -w /w <образ ai-assistant/api:check> python scripts/smoke.py …`.

Вход на стенде — провайдер dev: логины `ivanov` (админ), `kim`, `smirnova`, `petrov`, `sidorova`,
пароль пустой. Ниже `BASE=http://127.0.0.1:18000`.

### B2. Smoke на настоящей модели

```bash
uv run python scripts/smoke.py --base-url http://127.0.0.1:18000 --admin ivanov
```

Без `--fake`: вопросы настоящие. Ожидается шесть ✓. Пункты «файл» и «документ» зависят от ответа
модели — при ✗ повтори до трёх раз и запиши все исходы и текст ошибки. Пункт «Админка» покажет
недоступные роли моделей — сверь со списком из инвентаризации.

### B3. Вызов инструментов и история

Через API (вход, создание чата, сообщение, чтение SSE — как делает `scripts/smoke.py`; можно
написать короткий скрипт на его функциях):

1. Загрузи текстовый документ на 20–30 «страниц» (≈ 80 тыс. символов с заголовками разделов и
   уникальной фразой в середине) и спроси о детали из середины.
2. В том же чате попроси: «Прочитай страницы с 10 по 12 и перечисли заголовки».
3. Задай уточняющий вопрос по только что прочитанному.

Для каждого ответа запиши из трассировки (`GET /api/admin/chats/<id>` под `ivanov`, поле `trace`
сообщения): `tools_offered`, вызванные инструменты и их статусы, `history_tool_steps`, блок
`context`, `prompt_tokens_estimate` и фактические `prompt_tokens` из события `usage`. Ожидается:
инструменты вызываются настоящими `tool_calls`; на шаге 3 `history_tool_steps` больше нуля.

### B4. Точность счёта токенов

Сравни `prompt_tokens_estimate` с фактическим `prompt_tokens` на трёх сообщениях разной длины
(короткое, с документом, после чтения страниц). Без токенизатора оценка идёт по длине текста и
должна быть **не ниже** факта.

Затем включи точный счёт: скопируй `tokenizer.json` чат-модели в
`~/ai-check/config/tokenizers/chat/tokenizer.json`, раскомментируй `APP_MODELS__CHAT__TOKENIZER`
в `check.models.env`, выполни `$DCC up -d api generator`. Повтори три сообщения: в трассировке
`tokens_exact: true`, расхождение с фактом — единицы процентов (шаблон чата добавляет служебные
токены). Запиши обе таблицы: от них зависит, сколько контекста реально доступно.

### B5. Предел контекста на настоящем vLLM

Цель — убедиться, что длинный диалог с инструментами не приводит к отказу модели по длине
промпта. Чтобы не набирать 131 тыс. токенов, временно уменьши окно приложения, **не трогая
модель**: в `check.models.env` поставь `APP_MODELS__CHAT__CONTEXT_LENGTH=16384` и
`APP_MODELS__CHAT__MAX_OUTPUT_TOKENS=2048`, `$DCC up -d api generator`.

В чате с документом из B3 отправь подряд 5–6 запросов «прочитай страницы N–M и перескажи» на
разные диапазоны. Ожидается: все ответы `completed`; в трассировке поздних ответов блок `context`
показывает усечение (`history_dropped`, `tool_results_truncated` или `tool_results_dropped`),
`peak_tokens` не больше `budget`; фактический `prompt_tokens` не превышает 16 384 − 2048.

Так проверяется логика приложения. Отказ самого vLLM по контексту ты уже видел в A2 — запиши,
как он выглядит, если приложение всё-таки его получит (`model_http_400` в событии `error`).

### B6. Исправления дефектов 4 и 5

- **Малый контекст.** `CONTEXT_LENGTH=8192`, `MAX_OUTPUT_TOKENS=1024`, перезапуск `api` и
  `generator`. Новый чат с документом из B3, вопрос по нему, затем уточняющий вопрос. Ожидается:
  оба ответа `completed` (раньше — «Сообщение слишком длинное»); в трассировке
  `attachments.shrunk: true`, `peak_tokens` не больше `budget` (7168). Если отказ остался —
  запиши код и текст ошибки и размеры частей из трассировки.
- **Оборванный ответ.** `MAX_OUTPUT_TOKENS=200`, режим размышлений включён (`"thinking": true` в
  теле сообщения), вопрос, требующий длинного ответа. Ожидается: статус `completed`,
  `finish_reason: length`, текст ответа заканчивается пометкой «[Ответ оборван: модель достигла
  предела длины ответа…]» — в том числе если самого текста нет.

После B5 и B6 верни в `check.models.env` боевые значения контекста и перезапусти `api` и `generator`.

### B7. Нагрузка: цели §18.4 на настоящей модели

Убедись, что модель свободна. Обычный вопрос вместо сценария fake-llm:

```bash
uv run python eval/load/run.py --base-url http://127.0.0.1:18000 --concurrency 10 --messages 30 --prompt 'Объясни в десяти предложениях, зачем компании нужны резервные копии данных.' --check --json ~/ai-check/load-10.json
```

Это критерий приёмки этапа 10: все ответы завершены, время до первого токена p95 ≤ 2 с, скорость
≥ 20 токенов/с на пользователя. Запиши таблицу отчёта целиком. Затем — запас:

```bash
uv run python eval/load/run.py --base-url http://127.0.0.1:18000 --concurrency 30 --messages 60 --admin ivanov --prompt 'Объясни в десяти предложениях, зачем компании нужны резервные копии данных.' --json ~/ai-check/load-30.json
```

Во время прогонов сними `nvidia-smi` (загрузка и память GPU чат-модели) и из `/metrics` vLLM —
`vllm:num_requests_running`, `vllm:num_requests_waiting`. С вопросом по базам знаний (цель «TTFT
с RAG p95 ≤ 4 с») — только если на стенде есть `embed` и `rerank`: создай под `ivanov` базу,
загрузи 2–3 документа, повтори прогон на 10 диалогов с вопросом по ним.

Если цели не достигнуты — это не дефект приложения сам по себе: запиши цифры, загрузку GPU и
очередь vLLM; решение (флаги, `max_num_seqs`, квантизация — §3.5 SPEC) принимает человек.
