# Проверка доработок архитектуры на рабочей станции (Windows + WSL2), 2026-11-12

Проверялась ветка `ccr-024c8c3b-cnj7hg`, коммит `c69b49d` (31 коммит поверх `main`): исполнитель генерации `generator`,
управление контекстом, наблюдаемость, исправления по нагрузочному тесту, файлы первого запуска, декомпозиция генерации и
синхронизация с AD в планировщике. Проверка началась 12 ноября в 21:05 по местному времени (UTC+4). Код продукта не менялся.
Предложенные правки лежат отдельными коммитами в `agent/workstation-check-improvements`.

## Итог

**Вливать в `main` можно, но после решения по дефекту 4 и с правкой дев-стенда (дефект 1).** Для боевого контура
(chat-модель с контекстом 131 072) блокеров нет. Всё, что песочница не проверяла, на стенде работает:

- **Автоматические проверки:** `make check: OK` с первого раза, pytest **377 passed, 6 skipped**, Vitest **76**, e2e **29 из 29**,
  у генерации в отдельном сервисе нет ни одного тайм-аута.
- **Исполнитель:** перезапуск `api` не прерывает ответ, очередь переживает отсутствие исполнителя, healthcheck, метрики,
  дашборд и инцидент `generator_health` работают.
- **Нагрузка:** 150 из 150 при 50 одновременных, POST p95 0,79 с, `idle in transaction` не больше 8. Оба исправления
  подтверждены. На живой модели первый токен приходил через 164 с, поток не оборвался.
- **Синхронизация с AD** идёт задачей `worker`, `api` её больше не ведёт.
- **Дефект 1 (дев-стенд):** `stop generator` обрывает ответы через 5 с вместо доработки. Причина — `watchfiles`. В проде не
  воспроизводится. Правка проверена.
- **Дефект 4 (контекст):** при контексте 8–16 тыс. токенов системная часть промпта не ужимается под бюджет. С большим
  документом каждое сообщение при 8K и уточняющий вопрос при 16K падают с «Сообщение слишком длинное». Нужно решение
  человека: чинить до слияния или считать модели с малым контекстом вне рамок.
- **Живая модель:** vLLM на этой сети не скачать, запуск llama.cpp не разрешён правами агента. Проверено на Ollama
  0.33.1 + `qwen3:4b` на RTX 5070. Пункт «предел контекста» на 8192 не проверялся, флаги парсеров `compose.prod.yml`
  тоже.

## 3. Живая модель

- **Почему не vLLM.** Сеть станции к Docker Hub, Hugging Face и ModelScope даёт 17–47 КБ/с. Образ `vllm/vllm-openai` для amd64 —
  9,74 ГБ (`sha256:91ee972ab751…`), веса Qwen3.5-4B — около 8 ГБ, вместе около четырёх суток. Флаги
  `--reasoning-parser qwen3 --enable-auto-tool-choice --tool-call-parser qwen3_coder` на настоящем vLLM **не проверены** —
  остаются на сервер.
- **Почему не llama.cpp.** GitHub даёт 600 КБ/с: сборка `b12321` для Vulkan (36 МБ) скачана за 41 с. Запуск
  `llama-server.exe` не разрешили права агента (код из внешнего источника). Если разрешить, этот путь проверит предел контекста
  без подмены Ollama.
- **Ollama.** Из реестра Ollama до 8 МБ/с. Модель `qwen2.5-coder:7b`, уже бывшая на станции, **для инструментов не годится**:
  3 из 3 раз вызов пришёл JSON в тексте ответа (`finish=stop`, `tool_calls=[]`) — это проблема В5. `qwen3:4b` даёт настоящий
  `tool_calls` 3 из 3. Контейнеры видят Ollama по `host.docker.internal:11434`. Видеопамять: 3,9 ГБ при контексте 8192,
  5,1 ГБ при 16 384.
- **Вызов инструментов.** Вопрос по факту из середины документа на 26 страниц 3 раза из 3 получил верный ответ со ссылкой на
  стр. 13 и цитатой. Нашёл его авто-поиск по фрагментам вложения, модель инструмент не вызывала. Запрос «прочитай страницы
  10–12» заставил модель вызвать `read_document(page_from 10, page_to 12)`. Так было в 2 попытках из 3, третья упала по
  дефекту 4. Сработало усечение: `tool_results_truncated: 1`, `peak_tokens` = `budget` = 12 288, ошибки модели нет.
- **Как это пришлось настроить.** При `MAX_OUTPUT_TOKENS=1024` все 7 ответов на «прочитай страницы…» закончились
  `finish_reason=length` пустым текстом: модель потратила лимит на размышления, см. дефект 5. Проверка инструментов шла с
  `CONTEXT_LENGTH=16384` (и столько же у Ollama) и `MAX_OUTPUT_TOKENS=4096`. При 8192 приложение отказывало до вызова модели,
  см. дефект 4.
- **Оценка токенов против факта.** У модели не задан `tokenizer`, приложение считает по длине текста. Оценка выше
  фактического `prompt_tokens` от Ollama: 3855 против 2723 (+42%), 11 742 против 9718 (+21%), 11 904 против 10 415 (+14%).
  Отказа сервера по контексту не было. Ошибка в безопасную сторону, но она усиливает дефект 4.

## 4. Дефекты

### Дефект 1 🔴 (дев-стенд). `stop generator` обрывает ответы через 5 секунд

Шаги: отправить `[[scenario:stream:300:100]] проверка`, через 3 с выполнить `$DC stop generator`.

Ожидаемо: команда ждёт, ответ дописан, статус «завершён». Фактически: остановка 5,3 с, ответ `interrupted`, текст пустой. 2
прогона из 2. Лог `generator`:

```text
[18:17:44] received signal 15, raising KeyboardInterrupt
completions.draining           active=1 grace_s=180
[18:17:49] SIGINT timed out after 5 seconds
[18:17:49] process has not terminated, sending SIGKILL
```

**Причина.** В `compose.dev.yml` исполнитель запущен под `watchfiles`. По SIGTERM тот шлёт процессу SIGINT, ждёт 5 с и
убивает его. Флаг `--sigint-timeout` в `watchfiles` 1.3.0 действует только на перезапуск при правке кода. При остановке
вызывается `process.stop()` со значением по умолчанию (`finally` в `run_process`). Поэтому дорабатывать нечего и при правке кода:
комментарий «идущие ответы при этом дорабатываются» на дев-стенде неверен. Прод запускает
`python -m app.cli generator run` напрямую со `stop_grace_period: 200s` — там дефекта нет.

**Правка** — отдельный коммит, только `deploy/compose/compose.dev.yml`. Тот же `watchfiles`, но через `python -c`, со сроком
190 с и для перезапуска, и для остановки. Проверено: остановка 30,1 с, ответ дописан. Правка кода посреди ответа даёт
`draining` → ответ дописан → перезапуск.

### Дефект 2 ⚠️. «0» исполнителей на дашборде не красный

Шаги: `$DC stop generator` → админка → «Дашборд».

У ячейки класс `text-destructive`, но такого цвета в теме нет: в `styles/index.css` нет `--color-destructive`, класс больше нигде
не используется. Вычисленный цвет — `oklch(0.21 0.02 265)`, как у подписи рядом. В остальных местах ошибки окрашены `text-red-600`
(44 раза). **Правка** — отдельный коммит, одна строка в `DashboardPage.tsx`: `text-red-600 dark:text-red-400`. Цвет
`oklch(0.577 0.245 27.325)`, prettier и eslint чистые.

### Дефект 3 ⚠️. `make smoke` падает на стенде с данными прежних этапов

Шаги: стенд с базой «Регламенты» (`regs`, 52 документа, создана 1 ноября) → `make smoke`.

Ожидаемо: шесть ✓. Фактически: ✗ «Вопрос по приложенному файлу: в ответе нет кодового слова: «Нашёл в документе: Кодовое слово
проекта: ЛАЗУРЬ-7 [1]»». В режиме `--fake` скрипт спрашивает `[[scenario:find]] «Кодовое слово»`. fake-llm берёт первую строку
с этими словами из системного промпта, а фрагменты базы знаний идут в нём раньше вложений. В документе `report` базы `regs` есть
«Кодовое слово проекта». Порядок «база → вложения» тот же, что в `main`, — это не регрессия. Но `scripts/smoke.py` в ветке новый,
и его проверка зависит от данных стенда.

**Правка** — отдельный коммит: в режиме `--fake` спрашивать «Кодовое слово проверки», как в самом вложении. С ней 6 ✓.

### Дефект 4 🔴 (модели с малым контекстом). Системная часть промпта не ужимается под бюджет

Шаги: живая модель с `CONTEXT_LENGTH=8192`, `MAX_OUTPUT_TOKENS=1024` → приложить DOCX на 26 страниц (101 заголовок) → любой вопрос.

Ожидаемо: ответ, при необходимости с усечением. Фактически: через 0,2 с ошибка «Сообщение слишком длинное для контекста модели»
(`message_too_long`). Модель не вызывалась, 2 попытки из 2. Так ошибка выглядит в чате — на скриншоте тот же случай при 16K
([скриншот](assets/improvements/10f-live-history-followup.png)).
Оценка частей приложением при бюджете 7168:

| Часть | Токенов |
| --- | --- |
| Описания 10 инструментов / с 4 инструментами документов | 2779 / **3666** |
| Базовый системный промпт | ≈ 1076 |
| Блок вложений: оглавление + начало документа (`outline_preview_chars` 6000) | **4172** (2565 при 1500) |
| Фрагменты RAG: `rag.context_share` 0,25 **от всего контекста** | до 2048 |

`build_messages` проверяет только «система + сообщение» и отказывает целиком. При этом части системы не ужимаются: размер начала
документа задан в символах, оглавление — до 200 строк, доля RAG считается от всего контекста, а не от остатка. Даже с
`outline_preview_chars=1500` сумма (7307) больше бюджета. При 16 384 / 4096 (бюджет 12 288) первый вопрос проходит в 2 случаях из 3,
а **уточняющий вопрос в том же чате падает всегда**, хотя история ещё не добавлена.

Влияние: на боевом контуре у `chat` контекст 131 072, там это не воспроизвести. Но любая модель на 8–16K (дев-машины, запасной
вариант на меньших картах) работает с большими вложениями только на первом сообщении или не работает вовсе. Пункт задачи «предел
контекста» на такой модели не достижим: приложение отказывает раньше. Текст ошибки вводит в заблуждение: длинное здесь не
сообщение.

Предложение (код не менял): считать долю RAG и размер блока вложений от остатка бюджета после инструментов и базы; при нехватке
сначала урезать начало документа и оглавление, а не отказывать; текст ошибки — «документы и инструменты не помещаются в контекст
модели». Нужно решение, входит ли это в ветку.

### Дефект 5 ⚠️. Ответ, обрезанный по `max_output_tokens`, пустой и «завершён»

Шаги: живая модель с размышлениями (Ollama их не отключает), `MAX_OUTPUT_TOKENS=1024` → «Прочитай страницы 10–12 приложенного
документа…».

Фактически: 7 ответов из 7 — `status=completed`, `finish_reason=length`, `completion_tokens=1024`, текст пустой. В чате только
«Размышления · 10 с» и пустое место, без пометки, что ответ обрезан
([скриншот](assets/improvements/10h-live-empty-answer-length.png)). На fake-llm и в проде (`max_output_tokens: 16384`) это
маловероятно, но при `finish_reason=length` и пустом ответе пользователю нужна пометка.

## 5. Наблюдения, не дефекты

- **`users.sync.done` пишется дважды:** второй раз от логгера `app.worker.exports`.
- **`generator_health` переоткрывает тот же инцидент:** `occurrences` 2, статус снова «новый». После восстановления он
  остаётся «новым» с системным комментарием и сам не закрывается.
- **Три `Traceback`** (`generator`, `worker`, `api`) — от моей двойной правки файла за 3 с: `KeyboardInterrupt` при импорте
  во время перезапуска. Ещё `api` при своём перезапуске оборвал открытый SSE («timeout graceful shutdown exceeded»). Ответ при
  этом завершился, браузер переподключился.
- **Метрики `generator`** после перезапуска процесса обнуляются, а размеченные счётчики появляются только после первого ответа.
- **В логах `generator`** на дев-уровне DEBUG много строк `httpcore`, и есть предупреждение `qdrant_client` «Api key is used
  with an insecure connection».
- **Ollama** игнорирует `chat_template_kwargs.enable_thinking`. Чтобы проверять режим без размышлений на живой модели, нужен vLLM.
