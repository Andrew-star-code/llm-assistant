## Этап 1. Вход, пользователи, роли, каркас админки

### План

1. Схема БД (§14): `users`, `roles`, `permissions`, `role_permissions`, `user_roles`, `sessions`,
   `login_events`, `audit_log`, `app_settings`; миграция 0002; генерируемый `docs/reference/db-schema.md`.
2. `core/storage` — интерфейс `Storage` и локальный том (фото из AD; ADR-0009).
3. `auth`: провайдеры `ldap` (bind по UPN с обходом контроллеров, поиск сервисной учёткой с
   экранированием, `userAccountControl`, `access_group` с вложенностью) и `dev` (seed-пользователи из
   конфига); нормализация логина; сессии cookie + Redis + `sessions`; CSRF double submit; выход.
4. `security`: журнал входов, защита от перебора по логину и IP (Redis), блокировка пользователей.
5. `users`: профиль, ФИО и форма обращения (§11.1), фото, синхронизация с AD (отключённых — блокировать
   и разлогинивать); `rbac`: роли отделов, правила, `group_roles`, `bootstrap_admins`, гранулярные права,
   системные роли `superadmin`, `admin`, `kb_manager`.
6. `audit` и `admin`: «Пользователи» (поиск, карточка, блокировка, разлогин, роли), «Входы»,
   «Журнал аудита», «Диагностика AD».
7. CLI: `ad check [--password-prompt]`, `ad sync`, `create-admin`.
8. Фронтенд: страница входа, проверка сессии, CSRF, меню пользователя, профиль, уведомление при первом
   входе, каркас админки с проверкой прав и разделами из п. 6.
9. Тесты: unit (нормализация, экранирование, ФИО, роли), интеграционные на testcontainers
   (PostgreSQL, Redis) и mock-AD, безопасность (§18.2: пустой пароль, экранирование, права
   админ-эндпоинтов, аудит), e2e входа.
10. Документация: README модулей, `guides/ad-setup.md`, `guides/add-admin-page.md`,
    `reference/permissions.md`, `architecture/security.md`, CHANGELOG.

## Этап 2. Ядро чата

### План

1. Схема БД (§14): `folders`, `chats`, `messages` (дерево через `parent_id`, `active_leaf_id`,
   полнотекстовый индекс `russian` и `pg_trgm`), `feedback`; миграция 0003.
2. `llm`: реестр моделей по ролям, клиент AsyncOpenAI, режимы thinking (`chat_template_kwarg`,
   `reasoning_effort`, `separate_model`, `none`), сэмплинг из конфига, подсчёт токенов
   (токенизатор модели, если задан; иначе оценка), разбор стрима vLLM (`reasoning`/`reasoning_content`).
3. Промпты Jinja2 в `config/prompts/`: базовые правила, пользователь (ФИО, должность, отдел, форма
   обращения — §11.1), служебный промпт заголовка.
4. `completions`: оркестратор без инструментов — сборка промпта, бюджет контекста (усечение старой
   истории), генерация фоновой задачей, события в Redis Stream `gen:{message_id}`, SSE с
   `Last-Event-ID` и heartbeat, «Стоп» через флаг в Redis, `interrupted` при перезапуске,
   перегенерация (сестринский ответ), автозаголовок служебной моделью.
5. `chats`: чаты, папки, закрепление, переименование, мягкое удаление, поиск по названиям и тексту
   с подсветкой; проверка владельца на каждом эндпоинте (IDOR, §18.2).
6. `feedback`: лайк и дизлайк с причинами и комментарием.
7. Фронтенд: SSE-клиент, лента сообщений (дерево, переключатель версий «‹ 2/3 ›»), поле ввода
   (Enter/Shift+Enter, черновики, «Стоп», «Размышлять»), блок размышлений, рендер Markdown, кода
   (Shiki, «Копировать») и формул (KaTeX, нормализация делимитеров, незакрытые блоки во время стрима),
   действия под ответом, история с группами по датам, папками, закреплением, поиском (Ctrl+K),
   виртуализацией; горячие клавиши; стартовый экран с примерами.
8. Тесты: unit (промпт, бюджет, делимитеры, рендер), интеграционные (стрим, переподключение, стоп,
   перегенерация, удаление, поиск, IDOR) на fake-llm, e2e по критериям этапа.
9. Документация: SSE-протокол (версия 1), README модулей, `guides/add-model.md`, CHANGELOG.

живого стека), прогон `eval/scenarios` против fake-llm (оценки судьи осмысленны только на настоящих
моделях). Ограничения песочницы те же, что на этапах 3–4 (образ воркера, веса bge-m3) — **на машине
разработчика: `make check` и демо ниже.**

### Демо-сценарий

```bash
make dev-up
```

1. Войдите «Сидорова Елена Николаевна» (юрист, роль `legal`): на стартовом экране карточки
   «Анализ договоров» и «ИТ-поддержка». Выберите «Анализ договоров» — индикатор с крестиком в поле
   ввода, «Размышлять» включено, примеры запросов сценария, подсказка «Приложите договор (DOCX или
   PDF)»; без файла кнопка отправки неактивна. Приложите любой договор и спросите «Найди риски» —
   в шапке чата значок сценария.
2. Войдите «Петров» (бухгалтерия): карточки «Анализ договоров» нет. Выберите «ИТ-поддержка» и
   спросите `[[scenario:find]] «первая линия ИТ-поддержки»` — ответ цитирует строку промпта
   сценария. Крестик на индикаторе в чате — сценарий сброшен, чат продолжается как обычный.
3. Войдите «Иванов» → Админка → «Сценарии» → «ИТ-поддержка»: промпт, модель, инструменты, базы,
   режим RAG, роли, примеры. Справа «Тестовый чат» → «Начать», задайте вопрос. Поменяйте промпт,
   «Сохранить» — следующее сообщение тестового чата и чатов пользователей уже с новой версией
   (без перезапуска); в «Журнале аудита» — `scenario.update` с изменёнными полями.
4. Создайте свой сценарий («Новый сценарий») с ролью, например «Отдел: Бухгалтерия», — он
   появится только у бухгалтеров. Ошибка в шаблоне (`{{ user.`) — понятное сообщение, не
   сохраняется.
5. `make eval-scenarios` — ответы на эталонные запросы и средняя оценка судьи по каждому
   сценарию (на настоящих моделях; на fake-llm оценок нет).

44. «Нужно вложение» проверяется сервером, только пока в чате нет ни одного файла; дальше вопросы

По проверке на рабочей станции — подтвердить при ревью:

46. Порог реранкера `rag.search.rerank.score_threshold` — 0,01 вместо стартовых 0,2 (§10.4: порог
    подбирается по eval). С 0,2 рабочая конфигурация на настоящих моделях теряла 7 из 48 ответов;
    0,01 — наибольший порог без потерь. Цена: порог почти не отсекает шум (у нерелевантных
    фрагментов баллы до ~0,03), пустой поиск будет реже, а «не нашёл» модель решает по содержанию
    фрагментов. Пересчитывать при смене реранкера, эмбеддингов или чанкинга.
47. Страховка задач воркера: любая непредвиденная ошибка → статус «ошибка» с причиной и инцидент
    `worker_failed` (повтор задачи не делается — пользователь загрузит файл заново, админ —
    переиндексирует). При старте воркер `files` ставит в очередь вложения «в очереди» и
    «в обработке» — повтор безопасен.
