## Этап 1. Вход, пользователи, роли, каркас админки

   и разлогинивать); `rbac`: роли отделов, правила, `group_roles`, `bootstrap_admins`, гранулярные права,

8. Фронтенд: страница входа, проверка сессии, CSRF, меню пользователя, профиль, уведомление при первом

## Этап 2. Ядро чата

### План

1. Схема БД (§14): `folders`, `chats`, `messages` (дерево через `parent_id`, `active_leaf_id`,
   полнотекстовый индекс `russian` и `pg_trgm`), `feedback`; миграция 0003.
2. `llm`: реестр моделей по ролям, клиент AsyncOpenAI, режимы thinking (`chat_template_kwarg`,
   `reasoning_effort`, `separate_model`, `none`), сэмплинг из конфига, подсчёт токенов
   (токенизатор модели, если задан; иначе оценка), разбор стрима vLLM (`reasoning`/`reasoning_content`).
3. Промпты Jinja2 в `config/prompts/`: базовые правила, пользователь (ФИО, должность, отдел, форма
   обращения — §11.1), служебный промпт заголовка.
4. `completions`: оркестратор без инструментов — сборка промпта, бюджет контекста (усечение старой
   истории), генерация фоновой задачей, события в Redis Stream `gen:{message_id}`, SSE с
   `Last-Event-ID` и heartbeat, «Стоп» через флаг в Redis, `interrupted` при перезапуске,
   перегенерация (сестринский ответ), автозаголовок служебной моделью.
5. `chats`: чаты, папки, закрепление, переименование, мягкое удаление, поиск по названиям и тексту
   с подсветкой; проверка владельца на каждом эндпоинте (IDOR, §18.2).
6. `feedback`: лайк и дизлайк с причинами и комментарием.
7. Фронтенд: SSE-клиент, лента сообщений (дерево, переключатель версий «‹ 2/3 ›»), поле ввода
   (Enter/Shift+Enter, черновики, «Стоп», «Размышлять»), блок размышлений, рендер Markdown, кода
   (Shiki, «Копировать») и формул (KaTeX, нормализация делимитеров, незакрытые блоки во время стрима),
   действия под ответом, история с группами по датам, папками, закреплением, поиском (Ctrl+K),
   виртуализацией; горячие клавиши; стартовый экран с примерами.
8. Тесты: unit (промпт, бюджет, делимитеры, рендер), интеграционные (стрим, переподключение, стоп,
   перегенерация, удаление, поиск, IDOR) на fake-llm, e2e по критериям этапа.
9. Документация: SSE-протокол (версия 1), README модулей, `guides/add-model.md`, CHANGELOG.

## Этап 8. Лимиты

### План

1. **Модель и конфиг** (§12, §14): таблицы `limit_policies` (scope `global` / `role` / `user`,
   метрика, окно, лимит, роль модели, только thinking, срок действия, заметка, автор) и
   `usage_records` (пользователь, чат, сообщение, роль модели, вид — `chat`, `title`, `guard`;
   токены входа, выхода и размышлений, время), партиционирование по месяцам — разделы на месяц
   вперёд создаёт задача `scheduler`, плюс раздел по умолчанию на случай пропуска (миграция 0009).
   Глобальные политики по умолчанию — `limits.defaults` в `config/app.yaml` (значения §12.1);
   глобальная политика из админки перекрывает строку конфига с тем же ключом.
2. **Метрики** (§12.1): `messages` (запросы на генерацию: сообщение, правка, перегенерация),
   `tokens` (вход + выход, включая размышления), `concurrent_generations`, `uploads` (вложения чата
   и документы личной базы), `personal_kb_storage` (МБ) и `personal_kb_documents` — квота личной
   базы переезжает из `kb.personal_quota` в политики и становится настраиваемой по ролям (§7.8).
   `code_runs` — этап 11 (`TODO(stage-11)`).
3. **Эффективный лимит** (§12.2): по ключу «метрика + окно + роль модели + thinking» —
   персональная политика (не истёкшая), иначе максимальная из ролевых, иначе глобальная. Политика с
   ролью модели или `thinking` действует только на такие генерации. Временная политика истекает
   сама: проверка `expires_at` при каждом расчёте, без фоновых задач.
4. **Счётчики** (§12.3): Redis, окна по календарным границам в поясе компании (минута, час, день,
   неделя с понедельника, месяц). Один скрипт Lua атомарно проверяет все применимые лимиты и
   резервирует `messages` и слот генерации; при превышении — 429 `limit_exceeded` с
   `{metric, window, limit, used, reset_at}` и понятным текстом. Токены проверяются до запроса, а
   списываются по факту после ответа (перерасход последним ответом допускается), каждое списание —
   строка в `usage_records`. Слот одновременной генерации — сортированное множество с тайм-аутом:
   его продлевает живая генерация, а после падения процесса он освобождается сам.
5. **Применение**: отправка, правка и перегенерация сообщения; загрузка вложения и документа
   личной базы; ответы со статусом `stopped`, `error`, `interrupted` тоже списывают фактические
   токены; заголовок и guard пишутся в `usage_records`, но лимит пользователя не расходуют.
6. **API**: `GET /api/limits` — все метрики пользователя с остатком и временем сброса и «ближайшая
   к исчерпанию»; событие SSE `limits` в конце ответа; админка — `GET/POST/PATCH/DELETE

   сроком. Право `admin.limits.manage`, все изменения — в аудит.
7. **Фронтенд** (§12.4): индикатор в поле ввода по метрике, ближайшей к исчерпанию («Осталось 37
   из 200 сообщений · обновится в 00:00»), блокировка поля при исчерпании с пояснением; раздел
   «Лимиты» в профиле (полосы по всем метрикам); админка «Лимиты» — редактор политик и эффективные
   лимиты пользователя; блок лимитов в карточке пользователя (сброс, временное повышение).

## Этап 9. Семантический слой и SQL

### План

1. **Сервис `services/data-gateway`** (FastAPI, §9.5): каталог YAML `catalog/` — `sources.yaml`,
   `datasets/*.yaml`, `functions/*.yaml` — перечитывается без перезапуска (по времени изменения
   файлов); пароли источников — из секретов. Модель видит только описанные наборы и функции.
2. **Проверка SQL** (sqlglot, диалект T-SQL): ровно одно выражение SELECT или WITH; отказ для
   изменений данных и схемы, `EXEC`, `OPENROWSET`, `OPENQUERY`, `OPENDATASOURCE`, `xp_*`/`sp_*`,
   `SELECT INTO`, переменных и временных таблиц, таблиц и колонок вне наборов, доступных ролям
   пользователя. Затем RLS (представление набора заменяется подзапросом с условием по атрибутам
   пользователя, например отдел), ограничение `TOP 1000`, тайм-аут 15 секунд, выполнение под
   логином только на чтение, транзакция всегда откатывается.
3. **Функции** — параметризованный SQL с типизированными и проверяемыми параметрами (строка, целое,
   дата; обязательность, границы, длина); `search_employees` по представлению телефонного
   справочника.
4. **Идентичность пользователя**: `api` передаёт логин, роли и отдел в подписанном HMAC заголовке
   (общий секрет, срок 60 секунд); без верной подписи шлюз отвечает 401 — модель её не подделает.
5. **Подключение**: прод — MS SQL через SQLAlchemy + pyodbc (Microsoft ODBC Driver 18) в образе
   шлюза; дев-стенд — контейнер MS SQL Developer с тестовым справочником (`mock-mssql`). В тестах
   pytest шлюз работает в процессе с источником SQLite: проверенный T-SQL переводится sqlglot в
   диалект источника, поэтому правила проверки одни и те же; настоящий T-SQL через ODBC проверяет
   `make test-data-gateway` (образ шлюза против контейнера MS SQL).
6. **Инструменты** (§9.2): `list_datasets`, `describe_dataset` (колонки, связи, метрики и до 5
   похожих примеров «вопрос → SQL» по эмбеддингам), `call_data_function`, `run_sql_query` (до 50
   строк модели, полный результат — CSV-карточкой, не больше 3 неудачных попыток на ответ),
   `search_employees`. Предлагаются, только если шлюз настроен (`data_gateway.url`).
