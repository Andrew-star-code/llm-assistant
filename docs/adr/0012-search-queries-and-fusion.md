# 0012. Запросы dense и BM25 отдельно, слияние RRF в api

- Статус: принято
- Дата: 2026-10-31
- Уточняет: [ADR-0006](0006-hybrid-search-rerank.md)

## Контекст

ADR-0006 и §10.4 описывают один запрос Query API на коллекцию: prefetch `dense` + prefetch `bm25`
→ RRF внутри Qdrant. Но §10.4 и критерии этапа 4 требуют ещё двух вещей: в трассировке сообщения —
ранги каждого кандидата в dense и в BM25 и балл RRF; при отказе одного из запросов — искать по
оставшемуся. Слитый ответ Qdrant содержит только итоговый балл, а сбой одного prefetch роняет весь
запрос.

## Решение

- В каждой доступной коллекции два параллельных запроса — `dense` (40) и `bm25` (40), фильтр прав
  передаётся в каждый явно. Слияние — в api: RRF `1 / (60 + ранг)` (как в Qdrant) или DBSF
  (`rag.search.fusion`). Кандидаты всех коллекций сливаются в один список без дублей.
- Отказ запроса или эмбеддинга → стадия помечается `skipped` в трассировке, поиск идёт по
  оставшемуся списку; инцидент `rag_degraded` — не чаще раза в 10 минут (отметка в Redis).
- BM25 считает Qdrant (`qdrant/bm25`, `russian`, `avg_len` из конфига) — проверено на v1.19.2:
  точные коды вида `17-42/Б` и другие словоформы находятся. Провайдер `fastembed` — запасной,
  интерфейс оставлен (`rag.search.bm25.provider`, `TODO(stage-10)`).
- Id точки — `uuid5(document_id:version:chunk_index)`: соседние чанки достаются по вычисленным id
  без поиска, новая версия документа пишется рядом со старой и затем вытесняет её.

## Альтернативы

- Один Query API с prefetch: на запрос меньше, но нет рангов для трассировки и деградации по одной
  стадии. Вернуться можно, если задержка станет проблемой: трассировку тогда получать отдельными
  запросами только при включённой отладке.
- Слияние в Qdrant через `query_points_groups` — то же ограничение.

## Последствия

- Два запроса вместо одного на коллекцию; при 40 + 40 кандидатах и индексе в ОЗУ это единицы
  миллисекунд.
- Результат совпадает с RRF Qdrant при тех же списках; параметры по-прежнему меняются только по
  `eval/rag`.
