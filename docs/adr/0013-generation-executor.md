# 0013. Генерация ответа — в отдельном процессе-исполнителе

- Статус: принято
- Дата: 2026-11-11

## Контекст

По [ADR-0003](0003-sse-redis-streams.md) ответ генерирует фоновая asyncio-задача внутри процесса
`api`. Любой перезапуск `api` — выкатка, падение, правка конфигурации — прерывает все идущие
ответы: пользователь видит «Генерация прервана» и теряет минуты работы модели и инструментов.
`api` перезапускается чаще всего остального: в нём весь HTTP-код, админка и права.

При этом сам протокол к процессу не привязан: события идут через Redis Stream `gen:{id}`,
«Стоп» — флагом в Redis, признак живости — ключом `gen:alive:{id}`. `api` только создаёт задачу.

## Решение

Генерацию выполняет отдельный сервис `generator` — тот же образ и код, что у `api`, команда
`python -m app.cli generator run`.

- **Очередь.** `api` сохраняет вопрос и пустой ответ `streaming`, как раньше, и кладёт задание
  в список Redis `gen:queue` (`RPUSH`). Исполнитель забирает его (`BLPOP`) и запускает ту же
  `GenerationManager`-задачу. Исполнителей может быть несколько — задание получает один.
- **Ожидание в очереди.** При постановке `api` ставит `gen:alive:{id}` на
  `generation.queue_ttl_seconds`: пока задание ждёт (исполнитель перезапускается или занят),
  ответ не считается осиротевшим. Исполнитель берёт задание, только если ключ ещё жив
  (`SET … XX`), и дальше продлевает его, как раньше. Не дождалось — ответ помечает
  `interrupted` прежняя проверка осиротевших.
- **Одно исполнение.** Задание удаляется из очереди при получении и не переигрывается: упавший
  посреди ответа исполнитель оставляет `interrupted` (как сейчас упавший `api`). Повтор с начала
  задвоил бы уже отправленные пользователю события.
- **Остановка без потерь.** По SIGTERM исполнитель перестаёт брать задания и дорабатывает свои до
  `generation.shutdown_grace_seconds`; не успевшие сохраняются как `interrupted`. Новые сообщения
  в это время ждут в очереди следующего исполнителя.
- **Предел параллельности.** Исполнитель ведёт не больше `generation.max_concurrent` ответов;
  остальные ждут в очереди — это общий вход к модели для всех пользователей.
- **Режим `inline`.** `generation.mode: inline` оставляет задачу в процессе `api` — для тестов и
  запуска без отдельного сервиса (как `worker.eager` у файлов).

SSE-эндпоинт, «Стоп», протокол событий, лимиты и проверка осиротевших не меняются.

## Альтернативы

- **Оставить в `api`, увеличить время остановки.** Пока `api` дорабатывает ответы, он не
  принимает запросы: простой для всех вместо прерывания у немногих.
- **Две копии `api` и поочерёдный перезапуск.** Ответ всё равно живёт в памяти процесса, который
  надо остановить; ждать пришлось бы столько же, плюс балансировка в nginx.
- **Celery** (уже есть для файлов). Генерация — сотни одновременных долгих асинхронных стримов;
  prefork-воркеры Celery рассчитаны на короткие синхронные задачи, а asyncio-цикл внутри задачи
  пришлось бы изобретать. Свой цикл `BLPOP` — десятки строк.
- **Redis Streams с группой потребителей и повторной доставкой.** Повторная доставка здесь вредна
  (см. «Одно исполнение»), а без неё группа ничего не даёт сверх списка.

## Последствия

- Выкатка `api` не трогает идущие ответы; перезапуск `generator` их дорабатывает. Порядок
  обновления без ожидания (поднять новый исполнитель рядом, затем остановить старый) — в
  runbook этапа 10.
- Ещё один сервис в compose и ещё одна точка отказа: если исполнителя нет, сообщения ждут
  `queue_ttl_seconds` и завершаются как прерванные. Нужны его healthcheck и алерт «очередь не
  разбирается» (§16.6, этап 10).
- §2.2 SPEC: «`api` ставит задание, `generator` выполняет». Процесс `api` больше не обращается
  к чат-модели для ответов (служебные вызовы — как раньше).
- Логи генерации — в контейнере `generator`; `request_id` запроса передаётся в задании, чтобы
  строки сходились.
