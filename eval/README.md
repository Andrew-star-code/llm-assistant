# eval

Оценка качества (§10.6, §18). Прогоняется при смене моделей, чанкинга и параметров поиска.

| Набор | Что считает | Запуск |
| --- | --- | --- |
| `scenarios/` | По 10–20 эталонных запросов на каждый встроенный сценарий с критериями (`<код>.yaml`): модель сценария отвечает с тем же системным промптом, что в чате (без RAG и инструментов), служебная модель ставит оценку 1–5 по критерию; средняя сравнивается с прошлым прогоном (`baseline.json`) | `make eval-scenarios` или `uv run python eval/scenarios/run.py [--only <код>]` |
| `rag/` | hit@5 и MRR поиска по базам знаний для четырёх конфигураций: только dense, только BM25, гибрид без реранкера, гибрид с реранкером; разбивка по типам вопросов (точные коды, словоформы, перефразы, английские термины); вопросы без ответа в корпусе — отдельно; перебор порога реранкера | `make eval-rag` (на моделях стенда, отчёт — `eval/rag/report.json`) или `uv run python eval/rag/run.py [--check] [--json report.json]` с `APP_*` |

| `load/` | Нагрузочный тест чата (§18.4): N виртуальных пользователей входят, создают чат, отправляют сообщение и читают SSE до конца — тем же путём, что браузер. Отчёт: приём сообщения, время до первого токена, длительность, скорость генерации (p50/p95/max), сверка с целями | `make load-test` (дев-стенд, fake-llm) или `uv run python eval/load/run.py --help` |

`rag/corpus/` — небольшой корпус документов, `rag/questions.yaml` — вопросы с ожидаемыми документами.
Корпус индексируется тем же кодом, что и базы знаний, в отдельную коллекцию `eval_rag_chunks`
(удаляется после прогона). `--check` завершается с ошибкой, если рабочая конфигурация (гибрид с
реранкером) хуже любой другой по hit@5 или MRR.

**Порог реранкера** (`rag.search.rerank.score_threshold`). Вопросы типа `no_answer` (ответа в корпусе
нет) в hit@5 и MRR не входят — по ним видно, сколько раз поиск честно вернул пустой список. По
трассе рабочей конфигурации скрипт повторяет отбор для сетки порогов (без новых запросов к моделям)
и печатает таблицу «порог → hit@5, MRR, пустые ответы» и `recommended_threshold` — наибольший порог
без потерь относительно порога 0. Стартовое значение 0,005 нарочно с уклоном в шумный поиск: на
тестовом корпусе верные фрагменты коротких запросов получали от 0,011, а потерянный ответ хуже
лишнего фрагмента. Окончательное значение подбирают на реальных документах (ниже).

### Подбор порога на реальных документах

Скрипт умеет работать по настоящим базам знаний — уже проиндексированным, без записи и
переиндексации:

1. Составьте вопросы в `eval/rag/local/questions.yaml` (каталог не в git: вопросы и названия
   документов бывают внутренними) — формат тот же, что у `eval/rag/questions.yaml`, но `expected` —
   **название документа в базе**, как в админке. Нужны вопросы всех типов, особенно короткие (коды,
   номера, термины: у них самые низкие баллы) и 10–20 % вопросов `no_answer` — то, чего в базах нет,
   но о чём спросят. Хватит 50–100 вопросов; больше — точнее.
2. Прогон по кодам баз (через запятую):

   ```bash
   make eval-rag KB=regulations,it-docs QUESTIONS=eval/rag/local/questions.yaml
   ```

   Опечатки в названиях документов скрипт печатает как «ВНИМАНИЕ: в базах нет готового документа».
   Порог в отчёте — тот, что действует в чате (с поправкой из админки).
3. Выберите порог по таблице: `recommended_threshold` — без потерь; выше — меньше шума ценой
   потерянных ответов (сколько именно — в той же таблице). Подробно — в разделе «Как выбрать порог»
   ниже.
4. Поставьте его в админке «Базы знаний» → «Параметры поиска» (действует со следующего поиска,
   без перезапуска, пишется в аудит; «Вернуть из конфигурации» — снова значение из
   `config/app.yaml`). Когда значение устоится, перенесите его в `config/app.yaml`.

### Как выбрать порог

- В таблице важны две колонки «пусто»: «есть ответ» — потерянные ответы (должно быть 0), «нет
  ответа» — сколько шума порог отсёк (чем больше, тем лучше).
- Если на `recommended_threshold` вопросы без ответа уже отсекаются — берите его. Если нет, баллы
  верных фрагментов и шума перекрываются: порог выше `recommended_threshold` уменьшит шум только ценой
  потерянных ответов. По умолчанию выбираем полноту: лишние фрагменты модель отбрасывает по
  содержанию.
- Один вопрос из 50 — 2 % hit@5: разница в один-два вопроса между соседними порогами — шум выборки.
- Порог привязан к модели: при смене реранкера, эмбеддингов или чанкинга — подбирать заново.

## Прогон `eval/rag` на рабочей станции (Windows + WSL2)

Нужны только эмбеддинги и реранкер — те же bge-m3 и bge-reranker-v2-m3, что на сервере; чат-модель
не используется. Работает на CPU, видеокарта не обязательна.

1. Docker Desktop с интеграцией WSL2 (Settings → Resources → WSL integration), в дистрибутиве WSL —
   `git`, `make`, `uv`, Node 22 и pnpm. Репозиторий клонируйте **в файловую систему WSL**
   (`~/src/llm-assistant`), а не в `/mnt/c/…`: там медленный ввод-вывод и проблемы с правами.
   Чтобы `git push` из WSL не зависал молча на запросе пароля, подключите менеджер учётных данных
   Git for Windows:
   `git config --global credential.helper "/mnt/c/Program\ Files/Git/mingw64/bin/git-credential-manager.exe"`.
2. Дайте WSL не меньше 22 ГБ памяти (`%UserProfile%\.wslconfig`: `memory=22GB`, затем
   `wsl --shutdown`): TEI на CPU держит bge-m3 в ~12 ГБ, реранкер — ~2,2 ГБ (до 7 ГБ при прогреве).
   Реранкер стартует только после готового embed и не перезапускается вместе с Docker — иначе оба
   прогреваются одновременно и не помещаются в память; после перезагрузки — снова
   `make dev-models-up`. Если Docker Desktop не видит дистрибутив, включите его в Settings →
   Resources → WSL integration. pnpm нужной версии: `corepack install -g pnpm@10.28.0`.
3. Подняв стенд, запустите реранкер (первый раз скачиваются веса ~2,3 ГБ) и подключите его к api:

   ```bash
   make dev-up
   ```

   ```bash
   make dev-models-up
   ```

   ```bash
   cp deploy/compose/api.local.env.example deploy/compose/api.local.env
   ```

   Раскомментируйте в `api.local.env` блок «Настоящий реранкер», затем:

   ```bash
   docker compose --env-file deploy/compose/.env -f deploy/compose/docker-compose.yml -f deploy/compose/compose.dev.yml up -d api
   ```

4. Прогон (на CPU — 5–20 минут: реранк 56 вопросов по 60 кандидатов):

   ```bash
   make eval-rag
   ```

   Первой строкой скрипт печатает, на каких моделях идёт прогон (`BAAI/bge-m3`, реранкер
   `BAAI/bge-reranker-v2-m3 (tei)`), — если там fake-модели, `api.local.env` не подхватился.
   Тайм-аут реранкера в eval — 120 с (`--rerank-timeout`): eval меряет качество, а не скорость. Если
   реранкер всё же не ответил, `--check` падает с «стадия rerank пропущена», а не выдаёт ложную
   победу гибрида без реранкера.
5. Результат (таблицы, промахи и `recommended_threshold`; полный отчёт — `eval/rag/report.json`)
   пришлите или занесите в `docs/status.md` у критерия этапа 4. Если рекомендованный порог
   отличается от `config/app.yaml`, поменяйте его и прогоните ещё раз.


## Нагрузочный тест

```bash
make dev-up
```

```bash
make load-test
```

По умолчанию — 10 одновременных диалогов, 50 сообщений, ответ fake-llm ровным потоком
(`[[scenario:stream:300:30]]`: 300 слов, 33 слова/с). Против fake-llm цифры показывают накладные
расходы приложения (api, очередь и исполнитель генерации, Redis, SSE, PostgreSQL), а не модель.
`--check` завершает прогон с кодом 1, если не выполнены цели §18.4: все ответы завершены, время до
первого токена p95 ≤ 2 с, скорость генерации ≥ 20 токенов/с.

Больше нагрузки и настоящий сервер:

```bash
uv run python eval/load/run.py --concurrency 50 --messages 200 --admin ivanov
```

```bash
uv run python eval/load/run.py --base-url https://assistant.corp.local --provider ldap --logins test1,test2,test3,test4,test5 --password '…' --prompt 'Расскажи, чем занимается компания' --check
```

- **Лимиты.** У пользователя по умолчанию 2 одновременных ответа и 200 сообщений в сутки: на 10
  диалогов нужно 5 логинов. `--admin <логин>` временно (на 2 часа) поднимает лимиты тестовым
  пользователям через админ-API — политики видны в админке «Лимиты» и в аудите.
- **Предел исполнителя.** Сверх `generation.max_concurrent` (64) ответы ждут в очереди: время до
  первого токена растёт, это не ошибка. Ожидание видно в метрике
  `app_generation_queue_wait_seconds`.
- **Всплеск сообщений.** Больше 60 сообщений за 10 минут от одного пользователя заводят
  инцидент безопасности (`security.message_burst`) — берите больше логинов.
- Тест создаёт настоящие чаты тестовых пользователей; после прогона их можно удалить в админке.
